# 0035 Continuous backups: pgBackRest on a repository host, documents with rclone

Date: 2026-11-02 · Status: Accepted

## Context

ADR 0033 sets the recovery targets: at most **5 minutes of data lost** and **4 hours to restore service** after losing the server. Backups go to S3-compatible storage in the EU, in an account separate from the server's; the provider is chosen later, so the whole cycle has to work against any S3 service and be proven against a local stand-in. The brief is explicit that container images are not database backups.

What must be recoverable: the platform's database, Keycloak's and the CMS's (all three in one PostgreSQL cluster) and the documents in the object store (ADR 0029), which the database describes. Backups hold the same personal data as the platform, children's health and family details included, so they must be unreadable to the storage provider and to anyone who obtains the bucket's key alone (GDPR Art. 32). Erasure (Art. 17) must eventually reach the backups too.

Options checked on 2026-11-02:

| Option | State | Verdict |
| --- | --- | --- |
| Nightly `pg_dump` (what development has) | Logical, whole database each time | Up to a day of data lost: misses the 5-minute target |
| WAL-G | Active; S3, encryption with libsodium or OpenPGP | Capable; fewer verification tools and no repository host mode, so the database container would hold the storage key |
| Barman | Active; streams from a separate host; cloud upload through barman-cloud | Capable; two tool sets (Barman, barman-cloud) to reach S3 |
| **pgBackRest** 2.60.0 (PostgreSQL project's packages) | Active, supports PostgreSQL 18; full, differential and incremental backups; block-level incrementals; S3 with client-side AES-256 encryption; `verify`; a repository host over its own TLS protocol | **Chosen** |
| rclone v1.75.2 for the documents | Active; S3 to S3; `crypt` encrypts names and contents before upload | **Chosen**: Garage has no replication to another provider |

## Decision

**pgBackRest, with the backup service as its repository host.** The production PostgreSQL image carries pgBackRest; `archive_command` pushes every write-ahead log segment to a new `backup` service, which writes it to the off-site storage. `archive_timeout = 60` switches segments at least once a minute, so a change reaches the storage within about a minute even when the platform is quiet: well within 5 minutes. The `backup` service runs from the same image (so archiving and backups always use the same pgBackRest version) as the unprivileged `postgres` user, read-only, with no capabilities. It mounts the data directory read-only and shares PostgreSQL's local socket.

PostgreSQL talks to it only over pgBackRest's TLS protocol, presenting its own certificate from the platform's authority (ADR 0033, M8.4). The server accepts only the client named `postgres`, and only for the `pythagoras` stanza. So **the database stays on the internal network**, and neither the storage key nor the encryption passphrase is ever in the database's container. Only the backup service is on the `offsite` network, the one way out to the storage.

**Schedule and retention.** A full backup every Sunday at 01:00 UTC (or whenever the newest full is a week old); a differential every other day at the same time; the write-ahead log continuously. A fresh installation takes its first full backup as soon as the backup service starts. The service is healthy only once the log is being archived and a backup exists, so `up --wait` reports a stack without working backups. pgBackRest keeps **four full backups** with their differentials and the log in between: any moment of the last four to five weeks can be restored. Backups take an immediate checkpoint, use zstd compression, bundle small files and keep block-level maps, so differentials stay small. All three databases of the cluster are in every backup.

**Encryption before anything leaves the host.**
- The repository is encrypted with AES-256 (`repo1-cipher-type=aes-256-cbc`). The passphrase is `backup_cipher_pass`.
- The documents go through rclone's `crypt` layer, which encrypts both file names and contents. Its passphrase and salt are `backup_documents_pass` and `backup_documents_salt`.
- All three are generated by `scripts/prod-secrets.sh`, and **must be kept off the host as well** (the group's password manager, for example). Without them, a backup is useless once the server is gone.
- The storage key (`backup_s3_secret_key`) is issued by the provider. A key that can only reach the bucket, and that sits in an account separate from the server's, means a compromised server cannot reach other data. Equally, a compromised storage account yields only ciphertext.

**Documents: often, and before every database backup.** rclone copies the documents bucket every 5 minutes, and right before each database backup, as ADR 0029 asks ("objects first, then the database"). It reads with a key of its own that can only read the bucket. Since every version is its own object, written once, a copy only ever adds objects. An object that disappears from the bucket is moved aside under `removed/<time>` rather than deleted. Those copies are purged after 35 days, the age of the oldest database backup. So a database restored to any retained moment finds its documents, apart from versions uploaded in the last 5 minutes before a loss.

**Provider-neutral.** The storage is configured by endpoint, port, region, bucket, key and URI style (`.env.production.example`), plus an optional private certificate authority. Nothing else depends on the provider. `infra/backup-standin/compose.yaml` stands in for it until it is chosen: a Garage node behind TLS on the `offsite` network. `scripts/prod-stack-test.sh` proves the whole cycle against the stand-in in CI.

**Erasure and backups.** Data erased from the platform stays in the backups until they expire, at most five weeks; backups are not edited. This is a common and defensible position, provided that a restore re-applies the erasures completed since the backup was taken. The restore runbook (M8.7) does that from `privacy.data_subject_request`. The DPO should record this in the record of processing activities.

## Consequences

- Restores use `pythagoras-backup pgbackrest restore` from the backup service image, onto an empty data directory (M8.7 drills it and measures the time against the 4-hour target). The documents are restored first, from `sealed:current` plus `sealed:removed` up to the chosen moment.
- The development stack keeps its logical dumps (`scripts/db-backup.sh`, `scripts/db-restore-check.sh`). They prove a dump restores with every table, row and policy, and are not production's backups.
- Losing the off-site storage stops the archiving. PostgreSQL then keeps the write-ahead log locally, which grows until archiving works again. Monitoring (M8.6) alerts on archive failures and backup age before the disk fills.
- pgBackRest's TLS server and the database's certificate are renewed with the other certificates (`scripts/prod-secrets.sh`). The database's certificate now also allows client authentication.
- A second repository (for example a local one for faster restores, or a second provider) is a matter of a `repo2-*` section later; nothing in the design prevents it.
