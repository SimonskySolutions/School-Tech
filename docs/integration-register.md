# Integration register

Tracks every external dependency separately from implemented functionality. "Implemented" here means only what exists in this repository; nothing below has been validated against a real external system yet.

| System | Purpose | Contract known? | In the repository | External validation | Next step |
| --- | --- | --- | --- | --- | --- |
| Stripe (test mode) | Hosted checkout, payment events, refunds | Public API and webhook signing are documented | Adapter built: Checkout Session creation with an idempotency key, webhook signature and mode check, mapping of `checkout.session.*` events; unit-tested against the documented formats; on the production stack its requests are checked by Stripe's own `stripe-mock` (M8.8, ADR 0038), which sends no webhooks. Not built: payment retrieval, refunds, session expiry | None. **No account yet, by decision** (ADR 0010): built, not validated | Create a test-mode account, configure it (operations: Payments), run one real test payment and resend its webhook from the Stripe CLI |
| Development payment provider | Stand-in for Stripe until it is set up | Our own: HMAC-signed checkout tokens and events in Stripe's signature scheme | `apps/api/src/payments/development-provider.ts`; test checkout page under `/dev-payments/` (404 with Stripe or in production) | Exercised by the integration and end-to-end suites | Keep for development; never configured in production |
| Keycloak 26.8.1 | Single sign-on for staff and parents | Standard OpenID Connect; self-hosted, so fully under our control | Service, own database, development realm, users linked to seeded people; `scripts/identity-test.sh` | **Validated locally** (25 checks): realm security settings, real tokens, subject-to-person link, RLS per person | M1.3: token verification in the API (done). M3.2: accounts created through the admin API by the `pythagoras-provisioning` service account, validated locally (7 integration tests, ADR 0016). CMS editors sign in through the `pythagoras-cms` client (ADR 0019, 6 end-to-end tests). M7: SMTP for set-up e-mails. M8: production realm and staff MFA |
| Shkolo | E-diary: classes, timetables, grades, attendance, statutory school records | **Unknown.** No public API documentation found; to be settled later (decided 2026-11-01) | **Not built.** Development adapter: none (ADR 0032). `integration.external_reference` allows `shkolo` identifiers and holds none | None | Obtain Shkolo's API or export documentation and terms, a data-processing agreement for each direction, and the schools' agreement on which system is authoritative for what; then an ADR and contract tests before any adapter |
| Bulgarian accounting software | Journal entries, invoices, payments per entity | **Unknown.** No public API found for Ajur, Microinvest or Plus Minus; the software is to be confirmed (decided 2026-11-01: later) | The platform's own export of each company's ledger per period (M7.4, `docs/accounting-export.md`), labelled as not an import format | None | Ask the accountants which software and import format they use; add a matching export beside the platform's own |
| Statutory payroll and official reporting (НАП, НОИ, НЕИСПУО) | Payroll declarations, school reporting | Not in scope of the platform: stays in the payroll and accounting software and the schools' own systems (ADR 0028, 0032) | **Not built**, by design. No payroll data is kept; nothing reports to authorities. Development adapter: none | n/a | Confirm the boundary with the accountants and school administrations |
| Qualified e-signature | Signing contracts and consent forms | Depends on the Bulgarian qualified trust service provider, not chosen (decided 2026-11-01: later) | **Not built.** Development adapter: none (ADR 0032). Approvals and consents are records of a signed-in person's decision, not qualified signatures; documents signed elsewhere are filed (M6.4) | None | Choose a provider (for example Evrotrust, B-Trust, InfoNotary), with its contract, API and costs; then an ADR |
| E-mail | Notifications (ADR 0031) | Standard SMTP with TLS: any provider or the group's own server | Queue `notify.message`, worker sender over SMTP (Nodemailer), templates; development mailbox Mailpit in Compose | **Validated locally** against Mailpit (integration test); no production provider yet, by decision (2026-11-01) | Choose the provider, publish SPF, DKIM and DMARC, set the worker's SMTP settings (operations: Messages by e-mail) |
| SMS / Viber | Notifications | Provider APIs, not chosen | Nothing | None | Choose a provider if text messages are wanted; a further transport behind the same queue |
| Payload CMS 3.91.0 | School and group website content | Payload's REST API; self-hosted (ADR 0017) | `apps/cms` with its own database `pythagoras_cms` and role `pyth_cms`; one tenant per website (`org.website.cms_tenant_key`); the web app reads published pages | **Validated locally**: drafts never public, writes need an editor, the two databases cannot reach each other (6 integration tests, 5 end-to-end) | Editors sign in through Keycloak (done, ADR 0019); production image and migrations (M8). A website's tenant is created automatically by the platform (done, M3.5) |

Until a contract is confirmed, any adapter for these systems must be a clearly named development adapter and must not be described as an integration.

For Shkolo, qualified e-signature, statutory payroll and official reporting there is no adapter at all, not even a development one (ADR 0032); an architecture test (`apps/api/src/architecture.test.ts`) fails if code, pages or seeds name them, so nothing can present them as working before their contract exists.
